# DEFENSE — Завдання 3: Послідовність дій та середовище виконання (Sequence Diagrams)

### Намір і критерії (1–2 речення):
* **Намір** — Деталізувати внутрішню поведінку системи «Електронна Бібліотека» під час виконання обраного прецеденту **UC-05 (Створення запиту на Loan)** та розширення **UC-06 (Скасування Loan)** шляхом побудови трьох Sequence-діаграм у нотації PlantUML.
* **Критерії** — Наявність окремої діаграми на кожен із 3 сценаріїв (Main, Alternative ADR 0002, Extension); повна відповідність учасників сутностям ER-моделі Завдання 1 (`User`, `Book`, `Loan`) та шарам 3-ланкової архітектури (`UI`, `Controller`, `Service`, `Repository`, `DB`); наявність комбінованих фрагментів (`alt`, `opt`); некорректно не обірвані Activation Bars (тривають протягом усього процесу обробки); реалістичні інженерні назви методів API.

### Топ-3 розбіжності (spec ↔ артефакт) + коміт-виправлення:
• **Корекція обриву Activation Bar у блоці `alt`**: У первинній генерації ШІ лінія активації `LoanService` закривалася всередині гілки перевірки боргів `alt`. Виправлено: активацію `LoanService` винесено до входу у фрагмент `alt`, а деактивацію зафіксовано після повернення HTTP-відповіді (Коміт: `fix(seq): maintain continuous activation bar for LoanService across alt fragments`).
• **Деталізація методу перевірки боргів за ADR 0002**: Спочатку виклик перевірки мав абстрактну назву `checkUser()`. Виправлено: перейменовано на реалістичний SQL/DAO метод `checkActiveOverdueLoans(userId)` із чітким викликом SQL-запиту по атрибутах `returned_at IS NULL AND due_date < NOW()` (Коміт: `refactor(seq): explicitly model ADR 0002 SQL check in LoanRepository`).
• **Синхронізація розширювального сценарію UC-06**: Спочатку скасування бронювання було відмальовано як окремий ізольований процес без прив'язки до статусу `PENDING`. Виправлено: додано комбінований фрагмент `opt [Loan status == PENDING]` для деталізації зв'язку `<<extend>>` (Коміт: `docs(seq): add scenario 3 sequence diagram for UC-06 extend UC-05`).

### Ключове рішення — які альтернативи зважив і чому обрав цю (ADR):
Для відображення взаємодії обрано **класичну багаторівневу сервісну архітектуру (Web UI -> REST Controller -> Business Service -> DAO Repository -> SQL DB)**. Це дозволило наочно показати ізоляцію перевірки бізнес-правил (ADR 0002) у `LoanService` окремо від доступу до даних у `LoanRepository`, а також чітко продемонструвати обробку винятків з поверненням відповідей `HTTP 403 Forbidden` та `HTTP 201 Created`.

### Перевірка — узгодженість із попередньою моделлю (як перевірив):
1) **Із Завданням 1 (ER-модель):** Усі бази даних та репозиторії на діаграмах оперують виключно сутностями `User`, `Book` та асоціативною сутністю `Loan`, використовуючи бізнес-атрибути `borrowed_at`, `due_date`, `returned_at` та primary key `UUID`.
2) **Із Завданням 2 (Use Cases & Gherkin):** Сценарій 1 повністю реалізує успішне бронювання `US-02`; Сценарій 2 моделює відмову за становою вимогою `REQ-STA-02` (ADR 0002); Сценарій 3 деталізує прецедент `UC-06`, який розширює `UC-05` через `<<extend>>`.
