# Функціональні та Нефункціональні вимоги системи «Електронна Бібліотека» (EARS Syntax)

## 1. Функціональні вимоги (Functional Requirements)

### 1.1. Всюдисущі вимоги (Ubiquitous Requirements)
- **REQ-UBI-01**: Система ПОВИННА підтримувати унікальність ідентифікаторів `UUID` для кожної сутності (`User`, `Author`, `Book`, `Loan`).
- **REQ-UBI-02**: Система ПОВИННА зберігати дату створення запису та статус для кожного екземпляра `Loan`.

### 1.2. Подієві вимоги (Event-Driven Requirements)
- **REQ-EVT-01**: КОЛИ користувач подає запит на бронювання книги, система ПОВИННА створити запис `Loan` зі статусом `PENDING` та датою `borrowed_at = NOW()`.
- **REQ-EVT-02**: КОЛИ бібліотекар підтверджує повернення книги, система ПОВИННА оновити поле `returned_at = NOW()` у відповідному записі `Loan`.
- **REQ-EVT-03**: КОЛИ бібліотекар додає нову книгу, система ПОВИННА виконувати перевірку унікальності коду `ISBN`.

### 1.3. Станові вимоги (State-Driven Requirements)
- **REQ-STA-01**: ПОКИ користувач перебуває у статусі «Автентифікований» (`User`), система ПОВИННА надавати доступ до перегляду особистої історії `Loan`.
- **REQ-STA-02**: ПОКИ у користувача є хоча б один прострочений запис `Loan` (`returned_at IS NULL` ТА `due_date < NOW()`), система ПОВИННА блокувати можливість створення нових бронювань книг (реалізація ADR 0002).

### 1.4. Небажана поведінка (Unwanted Behavior / Exception)
- **REQ-EXC-01**: ЯКЩО користувач намагається забронювати книгу, яка відсутня в наявності, СИСТЕМА ПОВИННА повернути помилку `409 Conflict` та сповіщення «Книга недоступна».
- **REQ-EXC-02**: ЯКЩО вводиться некоректний формат `ISBN`, СИСТЕМА ПОВИННА повернути помилку `400 Bad Request`.

### 1.5. Опціональні вимоги (Optional Requirements)
- **REQ-OPT-01**: ДЕ доступний сервіс сповіщень, система ПОВИННА делегувати надсилання нагадувань про борги зовнішньому сервісу `Notification Service <<System>>`.

### 1.6. Вимоги поза межами системи (Out of Scope)
- **REQ-OUT-01**: Система НЕ ПОВИННА обробляти онлайн-оплату штрафів за прострочені книги у цьому релізі (перенесено на наступні версії, статус `UNCOVERED`).

## 2. Нефункціональні вимоги (Non-Functional Requirements / NFR)

### 2.1. Продуктивність та Швидкодія (Performance & Latency)
- **REQ-NFR-PERF-01**: Система ПОВИННА обробляти та повертати результати пошуку в каталозі книг (UC-01) за час, що не перевищує **200 мс** при 95-му перцентилі (p95).
- **REQ-NFR-PERF-02**: КОЛИ виконується перевірка активних заборгованостей користувача під час створення `Loan`, система ПОВИННА виконувати відповідний SQL-запит до БД не довше ніж за **50 мс**.

### 2.2. Безпека та Захист Даних (Security & Data Protection)
- **REQ-NFR-SEC-01**: Система ПОВИННА зберігати паролі користувачів у зашифрованому вигляді з використанням алгоритму **BCrypt** (з фактором вартості не менше 10).
- **REQ-NFR-SEC-02**: ПОКИ здійснюється мережева взаємодія між клієнтом та API системи, система ПОВИННА передавати всі дані виключно через зашифрований протокол **HTTPS (TLS 1.3)**.
- **REQ-NFR-SEC-03**: Система ПОВИННА використовувати коротвоживаючі **JWT-токени** для авторизації запитів користувачів після виконання `UC-03 (Log In)`.

### 2.3. Надійність та Доступність (Reliability & Availability)
- **REQ-NFR-REL-01**: Система ПОВИННА забезпечувати рівень доступності (Uptime) сервісу не менше **99.5%** на місяць.
- **REQ-NFR-REL-02**: КОЛИ виникає збій у зовнішньому сервісі `Notification Service <<System>>`, система ПОВИННА ізолювати помилку та продовжувати виконання основних операцій бронювання `Loan` без втрати цілісності даних.

### 2.4. Масштабованість та Масштаб (Scalability & Maintainability)
- **REQ-NFR-SCA-01**: Система ПОВИННА підтримувати одночасну роботу щонайменше **500 активних сесій** користувачів без деградації часу відгуку.
- **REQ-NFR-MAINT-02**: Усі сутності БД ПОВИННІ описуватися структурованими міграціями (DDL) із підтримкою зворотної сумісності.
