# ADR 0002: Перевірка прострочених видач при створенні нового Loan

- **Статус:** Accepted
- **Дата:** 2026-10-22

## Контекст та постановка проблеми
У системі "Електронна Бібліотека" користувачі можуть брати книги в тимчасове користування із фіксацією дати видачі (`borrowed_at`) та запланованої дати повернення (`due_date`). Якщо користувач вчасно не повертає літературу, виникає ризик блокування бібліотечного фонду та недоступності примірників для інших читачів. Як на рівні бізнес-правил системи запобігти накопиченню боргів у одного користувача?

## Розглянуті варіанти
1. **Дозволити необмежену кількість видач без перевірки боргів**: Система створює новий запис `Loan` незалежно від стану попередніх видач користувача.
2. **Блокувати створення нових видач при наявності боргів**: Перед створенням запису `Loan` система проводить перевірку на наявність хоча б одного простроченого запису (де `returned_at is NULL` та `due_date < NOW()`).
3. **Введення жорсткого ліміту на кількість одночасних книг (наприклад, не більше 3 книг)**: Обмеження загальної кількості активних видач незалежно від того, чи вони прострочені.

## Результат рішення
Обрано варіант **2 ("Блокування створення нових видач при наявності боргів")**.

Це рішення прямо реалізує станову вимогу `REQ-STA-002` та забезпечує баланс між гнучкістю використання бібліотеки та захистом її фонду.

### Наслідки
- **Добре:** Захищає бібліотечний фонд від систематичних неповернень та стимулює читачів вчасно повертати книги.
- **Добре:** Автоматизує роботу бібліотекаря — система самостійно відхиляє бронювання боржникам без залучення людського фактору.
- **Погано (Мінуси):** Вимагає додаткового SQL-запиту / перевірки стану активних `Loan` користувача при кожній спробі створення нового бронювання.
- **Нейтрально:** Якщо користувач має прострочену книгу, він все одно зберігає доступ до перегляду та пошуку в каталозі (`Guest` / `User` read-only права).

## Плюси та мінуси варіантів

### Дозволити необмежену кількість видач
- **Добре:** Проста реалізація без додаткових перевірок у БД.
- **Погано:** Високий ризик втрати книг, коли один користувач може забронювати десятки примірників і не повернути їх.

### Блокувати створення нових видач при наявності боргів
- **Добре:** Повністю вирішує проблему злісних боржників на рівні API.
- **Погано:** Потребує обробки відповідної помилки на UI та інформування користувача про причину відмови.
